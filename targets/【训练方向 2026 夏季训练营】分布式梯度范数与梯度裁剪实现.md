# 【训练方向 2026 夏季训练营】分布式梯度范数与梯度裁剪实现

# 1 背景与意义

在大模型训练中，**梯度范数（Gradient Norm）**是观察训练稳定性的重要指标，**梯度裁剪（Gradient Clipping）**则是抑制梯度爆炸、避免单次异常更新破坏训练进程的常用手段。

对于一组参数梯度 $g_1, g_2, \ldots, g_n$，`ClipGradNorm` 会将它们视为一个逻辑上的长向量，先计算总范数，再在范数超过阈值时对所有梯度使用同一系数进行缩放。这一行为在 PyTorch 中由 `torch.nn.utils.clip_grad_norm_()` 提供。

在单卡场景中，该功能可以通过遍历 `parameter.grad` 完成。但在 InfiniTrain 已支持的分布式训练中，梯度可能已被同步、分片、复制或存储在 flat buffer 中：

- DDP 的梯度在 DP ranks 上是副本，不应重复计入总范数。

- TP 同时存在分片参数和复制参数，前者需要聚合，后者需要去重。

- SP 下的部分复制参数可能只持有局部 sequence 的梯度贡献。

- PP / vPP 下每个 stage 只持有模型的一部分参数。

- InfiniTrain 当前的 ZeRO\-1 / ZeRO\-2 路径会让底层 optimizer 只消费本 DP rank 拥有的梯度 shard，其中 ZeRO\-2 不能依赖原始 `param.grad` 作为梯度真值来源。

因此，本项目并不是实现一个只能在单卡上工作的工具函数，而是要实现一个与 InfiniTrain 现有梯度同步和优化器数据流正确集成的**分布式梯度范数与梯度裁剪功能**。学员需要通过本项目串联 Autograd、DDP、TP、SP、PP 与 ZeRO 等相关模块，理解一份梯度从 backward 到 optimizer update 之间的完整过程。

# 2 问题描述

## 2\.1 目标

在 InfiniTrain 中实现 **`ClipGradNorm`**，并满足以下黑盒目标：

- 输入一组需要裁剪的逻辑参数、`max_norm`、`norm_type`、`error_if_nonfinite` 和 `foreach`。

- 原地修改这组参数对应的有效梯度，不修改参数本身。

- 返回**裁剪前**的全局总范数。

- 无论使用单卡、DDP、TP、SP、PP / vPP、ZeRO\-1、ZeRO\-2 或其现有合法组合，用户都使用同一套调用方式和参数语义。

公共入口必须是 `Optimizer` 类的虚成员函数，不能只提供一个独立工具函数。调用方应能通过 `std::shared_ptr<Optimizer>` 使用统一入口，由普通 Optimizer 和 `DistributedOptimizer` 根据各自实际管理的梯度提供多态行为。具体 C\+\+ 类型可以根据 InfiniTrain 风格调整，但参数和返回语义应尽量接近 PyTorch，例如：

```C++
auto total_norm = optimizer->ClipGradNorm(
    params_to_optimize,
    /*max_norm=*/1.0,
    /*norm_type=*/2.0,
    /*error_if_nonfinite=*/true,
    /*foreach=*/std::nullopt);
optimizer->Step();
```

对同一份未分片逻辑梯度，InfiniTrain 在任意并行布局下返回的总范数和裁剪后的逻辑梯度，应与 PyTorch 在完整参数上调用 `torch.nn.utils.clip_grad_norm_()` 的结果等价。

## 2\.2 原则

- **分层对齐**：数学结果以未分片逻辑梯度为基准；公共接口和边界行为以 PyTorch `torch.nn.utils.clip_grad_norm_()` 为基准；分布式梯度完成、副本过滤和统计量归约参考 Megatron\-Core；实际梯度存储和 ZeRO shard 以 InfiniTrain 当前数据流为准。

- **全局一致**：每个逻辑梯度元素在总范数中恰好计算一次，不因分片而漏算，不因副本而重复计数。

- **接口稳定**：通过 `Optimizer::ClipGradNorm_()` 提供统一入口，并行策略与 ZeRO 细节对用户透明，功能不依赖 example 中的临时 rank 判断或针对某个模型的特殊处理。

- **职责清晰**：梯度范数与裁剪只处理已属于本次 optimizer update 的有效梯度，不参与参数更新，不破坏现有 Autograd、bucket view 与 optimizer 逻辑。

## 2\.3 核心功能要求

**训练营规则上，项目的实现并无唯一技术路线要求。**下述要求主要约束对外行为与必须通过的特殊场景，具体类设计、元数据、通信组织和性能优化方式由学员自行调研与设计。

### 2\.3\.1 基本接口行为

1. `parameters` 表示需要裁剪的逻辑参数集合。传入 LoRA 或其他可训练参数子集时，不得裁剪集合外的梯度。

2. 无梯度的参数应被忽略。所有参数都无梯度时，返回值为 `0.0` 的标量 Tensor，不修改任何内存。

3. 核心实现至少支持 $L_1$、$L_2$、任意正有限 $p$ 与 $+\infty$ 范数，并与 PyTorch 结果对齐。

4. 返回值必须是裁剪前的 `total_norm`。对非空梯度，使用与 PyTorch 一致的系数：

```Plaintext
clip_coefficient = min(max_norm / (total_norm + 1e-6), 1.0)
```

5. 梯度必须原地缩放。范数不超过阈值时不得放大梯度，`max_norm == 0` 时不得将其解释为“关闭功能”。

6. `error_if_nonfinite=true` 且总范数为 `NaN` 或无穷时，必须在修改任何梯度之前报错；为 `false` 时，按 PyTorch 语义继续处理。

7. `foreach` 参数需要保留。`false` 使用基础路径，`std::nullopt` 允许框架自动选路；若基础项目未实现快速路径，`true` 必须给出明确的不支持错误，不得静默忽略。

8. CPU 和 CUDA 上都需要正确工作。

### 2\.3\.2 分布式与并行策略兼容

分布式行为参考 Megatron\-Core 的以下思路：在范数统计前确保本次 update 的梯度已完成累加与同步；计算范数时过滤 shared / TP duplicates；在能覆盖全部唯一梯度分片的通信范围中归约统计量。但最终的裁剪系数必须应用到本次 optimizer update 实际使用的所有梯度，不能只缩放参与范数统计的那一部分。

以下场景必须特别处理并通过测试：

1. **DDP**：范数必须基于 DDP 同步后的梯度计算。经典 DDP 中各 DP rank 上的梯度是副本，不能再将这些副本重复相加。

2. **TP**：TP\-sharded 参数的所有 shards 都要计入全局范数；TP\-replicated 参数只能计算一份副本，但所有将被更新的副本都必须被裁剪。

3. **SP**：对只持有局部 sequence 梯度贡献的复制参数，必须在计算范数和更新参数前得到正确的完整梯度。

4. **PP / vPP**：全局范数必须覆盖所有 pipeline stages 和 local chunks。普通 PP 参数是模型的不同部分，不应错误同步它们的参数梯度；如果存在 shared / tied 参数，不得重复计数。

5. **ZeRO\-1 / ZeRO\-2**：必须使用底层 optimizer 实际消费的本地梯度 shards 计算范数和执行裁剪，并通过分布式统计得到全局范数。不得把未同步区域、已过期数据或 bucket padding 计入范数，也不得依赖 ZeRO\-2 原始 `param.grad` 存在。

6. **混合并行**：在 DDP \+ TP \+ SP、TP \+ SP \+ PP / vPP \+ ZeRO 等现有合法组合中，同时满足上述分片、副本与梯度就绪规则。任何逻辑梯度元素都只能计算一次。

7. **Gradient accumulation 与 overlap**：只能在全部 micro\-batches 的梯度累加完成后裁剪一次。启用梯度通信重叠时，不得读写尚未完成通信的 bucket 或 shard。

### 2\.3\.3 工程集成要求

1. `ClipGradNorm_()` 必须作为 `Optimizer` 的公共虚接口提供，并能通过 `std::shared_ptr<Optimizer>` 正确动态派发。普通 Optimizer 应处理常规参数梯度，`DistributedOptimizer` 应在同一接口内处理梯度同步与 ZeRO shard；不能只实现独立 free function，或在 GPT\-2 / LLaMA\-3 example 中写特殊分支。

2. CPU / CUDA 上的范数归约、非有限检查与原地缩放需要纳入现有 Tensor / Dispatcher 体系，不得通过逐参数拷贝到 CPU 上实现 CUDA 路径。

3. 原地裁剪不得替换梯度 storage，不得破坏 `gradient_as_bucket_view`、flat buffer 或 ZeRO shard view 的别名关系。

4. GPT\-2 和 LLaMA\-3 example 都需要提供一致的 gflags 配置，建议形式如下：

```Plaintext
--clip_grad_norm=1.0
--grad_norm_type=2.0
--clip_grad_error_if_nonfinite=true
--clip_grad_foreach=auto
```

5. `clip_grad_norm < 0` 可作为 example 层的关闭开关；公共接口中的 `max_norm == 0` 仍需按 PyTorch 语义执行。

6. 训练 log 中应能记录每个 optimizer step 的 `total_grad_norm`、当前 learning rate 和 loss，便于数值对齐与问题定位。

### 2\.3\.4 正确性验证

项目必须同时提供单元测试、分布式测试和端到端对齐测试。

#### 2\.3\.4\.1 单元测试

CPU 和 CUDA 至少覆盖：

- 单参数、多参数、部分无梯度、全部无梯度。

$L_1$、$L_2$、非整数正 $p$、$+\infty$ 范数。

- 范数低于、等于、高于 `max_norm`，以及 `max_norm == 0`。

- `NaN`、`+Inf`、`-Inf` 梯度与 `error_if_nonfinite` 的 true / false 分支。

- FP32、BF16 / FP16（在 backend 支持范围内）。

- 裁剪前总范数、裁剪后梯度与 PyTorch 结果对齐，且原地裁剪不改变 data pointer / bucket view 关系。

#### 2\.3\.4\.2 分布式测试

至少覆盖：

1. DDP，分别开启与关闭 gradient bucketing。

2. TP，同时包含 TP\-sharded 与 TP\-replicated 参数。

3. TP \+ SP，包含需要同步局部梯度贡献的复制参数。

4. ZeRO\-1 与 ZeRO\-2，包含梯度 shard 落在参数中间、跨参数边界与 bucket padding 的情况。

5. PP / vPP，以及 `scripts/test_config.json` 中已支持的 TP \+ SP \+ PP \+ vPP \+ ZeRO\-1 混合场景。

6. Gradient accumulation 和 `overlap_grad_reduce=true`。

每个测试需要比较各 rank 返回的全局总范数、裁剪后的本地有效梯度以及一次 optimizer update。

分布式测试的数学 oracle 必须由逻辑完整梯度构建，可以在测试中 gather 后计算，或使用等价的未分片 PyTorch 模型。Megatron\-Core 用于参考分布式实现机制，不代替逻辑完整梯度 oracle。不能把每个 shard 上独立计算的范数当作全局结果。

#### 2\.3\.4\.3 端到端对齐

需要自行修改项目配套的 PyTorch GPT\-2 / LLaMA\-3 训练脚本，在相同初始权重、数据、有效 global batch size、learning rate 和 clipping 参数下，比较：

- 每一步裁剪前的 `total_grad_norm`。

- 裁剪后的梯度或一次参数更新。

- 至少 10 个 iteration 的 loss 序列。

对齐报告至少包含 GPT\-2 和 LLaMA\-3 两个模型，并覆盖以下 4 类 8 卡配置：

1. DDP=8，ZeRO 关闭。

2. DP=2，TP=4，ZeRO\-1。

3. DP=2，TP=4，SP 开启，ZeRO\-2。

4. DP=2，TP=2，SP 开启，PP=2，vPP=2，ZeRO\-1。

需要在报告中提供测试命令、log、误差阈值和误差分析。对 BF16 或不同 collective 顺序引入的浮点误差，应设置合理 tolerance，不得仅以“loss 能够下降”作为正确性证据。
